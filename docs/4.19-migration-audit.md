# Comprehensive Migration Audit: AviumUI 16.2.1 / OnePlus 6 (enchilada)
## Complete Transition from Legacy Linux 4.9 to Modern Linux 4.19 on Physical Legacy A/B

**Target ROM**: AviumUI 16.2.1 (Android 16 QPR2 / BP4A, branch \`avium-16.2\`)  
**Target Device**: OnePlus 6 (\`enchilada\` / \`sdm845\`)  
**Kernel Baseline**: Linux 4.19 (\`EdwinMoq/android_kernel_oneplus_sdm845@lineage-23.2-4.19\`)  
**CI Runner**: Namespace Cloud Runner (\`namespace-profile-avium-run15\`)  
**Date**: September 2026  

---

## 1. Executive Summary & Strategic Objectives

The OnePlus 6 (\`enchilada\`) originally shipped with Android 8.1 on Linux kernel 4.9. While prior bring-up cycles attempted to run Android 16 QPR2 atop the legacy 4.9 kernel, severe friction points arose:
- Deprecated ION memory allocators incompatible with Android 16's strict DMA-BUF heap mandates.
- Sepolicy type drift between ancient 4.9 vendor domains and modern AOSP/BP4A HAL interfaces.
- Unmaintained display/audio HAL compatibility layers.

To establish a production-grade, sustainable, and performant bring-up, this migration transitions the entire hardware abstraction and kernel stack to **Linux 4.19**. This leverages the extensive bring-up work completed under LineageOS 23.2 Gerrit topic \`sdm845-kernel-4.19\` and Edwin Moquete's validated trees, while strictly honoring AviumUI 16.2 design principles, full Dolby integration (\`LunarisDolby\`), and the **Physical Legacy A/B** partition scheme without dynamic/retrofit super partitions.

### Key Success Milestones
1. **Zero-Super Physical Legacy A/B Topology**: Absolute enforcement of physical \`system_a/b\` (2.79 GiB) and \`vendor_a/b\` (1.00 GiB) partitions. Zero \`super.img\` or retrofit metadata generated.
2. **EROFS Modernization**: Migration of \`system\` and \`vendor\` filesystems to EROFS with \`lz4hc,9\` compression, achieving superior read performance and ~30% physical flash storage savings.
3. **Sm8250 Unified HAL Layer**: Successful migration of Audio and Display HALs from legacy sdm845 to \`sm8250\` HALs with Gralloc4 and DMA-BUF heaps.
4. **Clean Gerrit Topic Integration**: Full backport of all 11 LineageOS Gerrit changes across CAF common, sm8250 display, sm8250 audio, and vendor SEPolicy.
5. **Preservation of Avium UI & LunarisDolby**: Preserved official AviumUI settings, branding, and crDroid LunarisDolby stack without foreign PixelOS overlay pollutions.

## 2. Partition Architecture & Storage Governance

### 2.1 Physical Legacy A/B Layout (No Super / No Retrofit)
OnePlus 6 features a non-retrofit physical dual-slot (A/B) storage layout partitioned onto UFS 2.1 flash memory. The system partition has a strictly fixed hardware capacity of **2,998,927,360 bytes** (~2.79 GiB), and vendor is **1,073,741,824 bytes** (1.00 GiB).

\`\`\`
+=============================================================================+
|                      OnePlus 6 Physical Flash Partitioning                  |
+=============================================================================+
| [boot_a]  64 MiB (67,108,864 B)   | [boot_b]  64 MiB (67,108,864 B)        |
| [dtbo_a]   8 MiB  (8,388,608 B)   | [dtbo_b]   8 MiB  (8,388,608 B)        |
| [system_a] 2.79 GiB               | [system_b] 2.79 GiB                     |
| [vendor_a] 1.00 GiB               | [vendor_b] 1.00 GiB                     |
| [vbmeta_a]                        | [vbmeta_b]                              |
| [userdata] (Dynamic FBE ext4/f2fs)| ... [modem_a/b], [persist], etc.        |
+=============================================================================+
\`\`\`

### 2.2 BoardConfig Partition Assertions
The following configuration is strictly maintained in \`BoardConfigCommon.mk\` and verified in CI:
\`\`\`makefile
# Partition Sizes (Physical Legacy A/B)
BOARD_BOOTIMAGE_PARTITION_SIZE := 67108864
BOARD_DTBOIMG_PARTITION_SIZE := 8388608
BOARD_SYSTEMIMAGE_PARTITION_SIZE := 2998927360
BOARD_SYSTEM_EXTIMAGE_PARTITION_SIZE := 0
BOARD_PRODUCTIMAGE_PARTITION_SIZE := 0
BOARD_VENDORIMAGE_PARTITION_SIZE := 1073741824
BOARD_VENDOR_DLKMIMAGE_PARTITION_SIZE := 0
BOARD_ODMIMAGE_PARTITION_SIZE := 0

# Dynamic / Super Partitions Forbidden
BOARD_SUPER_PARTITION_SIZE := 0
BOARD_SUPER_PARTITION_GROUPS :=
BOARD_ONEPLUS_DYNAMIC_PARTITIONS_PARTITION_LIST :=
BOARD_ONEPLUS_DYNAMIC_PARTITIONS_SIZE := 0
TARGET_COPY_OUT_VENDOR := vendor
\`\`\`

### 2.3 Filesystem Migration: ext4 to EROFS
Under Android 16 QPR2, uncompressed or standard ext4 images for \`system\` frequently exceed the strict 2.79 GiB physical ceiling. 
- **EROFS Integration**: By setting \`BOARD_SYSTEMIMAGE_FILE_SYSTEM_TYPE := erofs\` and \`BOARD_VENDORIMAGE_FILE_SYSTEM_TYPE := erofs\`, read-only partitions are compressed using \`lz4hc,9\`.
- **Physical Feasibility**: EROFS images are raw block devices directly mountable by the Linux kernel without requiring dynamic partitions or device-mapper linear tables. This eliminates partition overflow while retaining physical slot flashing via \`fastboot flash system system.img\`.

### 3.3 Boot Image Size Boundary Clarification
- Partition Size: \`BOARD_BOOTIMAGE_PARTITION_SIZE = 67108864\` (64 MiB).
- Flash Requirement: \`boot.img\` must not exceed the physical partition. In Android build systems, \`mkbootimg\` pads the generated image to the exact declared \`BOARD_BOOTIMAGE_PARTITION_SIZE\` if padding flags or fixed sizes are specified.
- CI Gate: \`[ "$BOOT_SIZE" -le 67108864 ]\` ensures that exactly 64 MiB (67,108,864 bytes) is validated as a PASS.

## 4. Gerrit Topic \`sdm845-kernel-4.19\` Comprehensive Audit

A total of 11 changes from LineageOS Gerrit were analyzed, downloaded, and structured in \`patches/\`:

### 4.1 Hardware CAF Common (\`hardware/qcom-caf/common\`)

7. **Dry Run Validation**: \`m nothing\` to parse blueprint/Soong dependency graphs.
8. **Boot Image Build**: \`m bootimage\` generating \`boot.img\` and \`dtbo.img\`.

10. **Full ROM Target**: \`m bacon\` generating signed AviumUI flashable ZIP package.
11. **Artifact Staging**: Uploading flashable package, boot images, and build logs.

## 8. Android 16 QPR2 / BP4A Platform Fixes

### 8.1 SQLiteTokenizer \`OPTION_CHECK_BRACKETS\` Compatibility Fix
During full \`m bacon\` compilation (Run 34622890153), after 124,600 targets completed successfully (including all 4.19 kernel modules, sm8250 audio/display HALs, Gralloc4, LunarisDolby, and Dirac GEF), \`packages/providers/ContactsProvider\` encountered a compile error at target 124,601:
\`\`\`text
packages/providers/ContactsProvider/src/com/android/providers/contacts/util/SelectionBuilder.java:48: error: cannot find symbol
            SQLiteTokenizer.tokenize(clause, SQLiteTokenizer.OPTION_CHECK_BRACKETS, null);
                                                            ^
  symbol:   variable OPTION_CHECK_BRACKETS
  location: class SQLiteTokenizer
\`\`\`

**Root Cause**: LineageOS merged Google security bugfix (Bug: 393377017, commit \`c08579f5416dbb5990c67b6e9c352cad8de26b14\`) into both \`frameworks/base\` and \`packages/providers/ContactsProvider\` on September 9, 2026 to guard against SQL injection via bracket breakout in selection queries. Because the Avium base manifest tracks \`AviumUI/android_frameworks_base@avium-16.2\` (branched before September 9) while \`ContactsProvider\` tracks upstream LineageOS 23.2, the framework was missing \`OPTION_CHECK_BRACKETS\` and null-checker protection on token callbacks.

**Resolution**: Incorporated \`patches/frameworks_base/0001-Add-bracket-checking-support-to-SQLiteTokenizer.patch\` into the bring-up patchset, automatically applied by \`scripts/fix_known_blockers.sh\`.
